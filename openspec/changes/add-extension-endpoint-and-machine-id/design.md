## Context

`add-extension-mechanism` established the `LSTK_EXT_*` runtime-context contract, and `add-extension-session-id` established the pattern this change follows: expose an internal value through a getter, add one `omitempty` field to the JSON context, populate it at the command boundary, and accept that absence is ambiguous rather than engineering the ambiguity away. Both new fields are that same shape.

What is new here is that one of them, `endpointUrl`, is not lstk's own state but a user-supplied value — which raises a question `sessionId` never did: how much of lstk's own interpretation should travel with it. `add-endpoint-url-flag` built a resolver that validates, normalizes, and probes; the decision below is that only the first stage of it belongs on this path.

## Decisions

### Decision 1: Convey the endpoint value verbatim — precedence only, no validation and no probe

`endpointUrl` is the raw winning source value. lstk applies its precedence (`--endpoint-url` > `LSTK_ENDPOINT_URL` > `AWS_ENDPOINT_URL`) and conveys the result unchanged: not parsed, not normalized, not checked for reachability or emulator type. The implementation is `endpoint.ResolvedSource`, not `endpoint.Resolve`.

**Rationale**: precedence is the one thing an extension genuinely cannot reproduce — it is lstk's policy, and re-implementing it in each extension would guarantee drift. Everything past that is judgment about the value, and judgment belongs to the consumer. `endpoint.Resolve` hard-fails on an unreachable or unclassifiable endpoint, which is correct for its existing callers (`aws`, `terraform`, `cdk`, `sam`, `az`, `reset`, `status`, `snapshot`) because they are about to make a request and need the emulator type. Dispatch is the opposite situation: lstk makes no request, and the first consumer of this field is a doctor whose entire purpose is diagnosing endpoints that fail exactly those checks. Probe-and-fail would make the tool refuse to start in the case it exists for, and would put a network round-trip in front of every extension dispatch that has `AWS_ENDPOINT_URL` set in the ambient environment. Passing the value through byte for byte also lets an extension report the user's actual mistake back to them, which a normalized value cannot.

**Alternatives considered**: full `Resolve`, as originally specced (rejected: breaks the primary consumer, as above, and imposes up to a 5s probe on an unrelated code path). Validate but do not probe, via a new `ResolveURL` helper (rejected: it splits the difference without buying anything — an extension that must handle an unreachable URL is already handling the untrusted case, so rejecting only the malformed subset adds an exported function and a failure mode while still leaving the consumer to validate; it would also strip a trailing slash and otherwise reshape the value the user typed). Conveying the source name alongside the value, e.g. `endpointSource: "AWS_ENDPOINT_URL"` (rejected: no consumer needs to act on which variable won, and it is trivially re-addable if one ever does).

### Decision 2: Convey the prepared machine id; the accessor owns the derivation, guarded and time-bounded

`machineId` is the salted hash `LoadOrCreateMachineID` produces (`dkr_`/`sys_`/`gen_` prefixed), never the raw Docker daemon id or `/etc/machine-id`. `MachineID(ctx)` derives it on first use through the client's `sync.Once` and memoizes it for the process; `GetEnvironment` reads it through the accessor, so the conveyed value and the value stamped on lstk's own events are the same by construction. Two guards live inside the accessor, in order: a disabled client returns empty *before* any computation happens, and the computation itself runs under a 3-second timeout (`machineIDTimeout` in `internal/telemetry/client.go`).

**Rationale — identity and the disabled guard**: the field's whole purpose is that lstk's events and the extension's report the same machine, so it must be the one memoized value, not an equivalently-derived one. Routing every consumer through one accessor guarantees that and makes ordering impossible to get wrong: whichever of dispatch or event-building runs first performs the derivation, the other reads the cache. Placing the `enabled` guard ahead of the computation is what makes the documented contract — "a disabled lstk computes neither" (the spec delta, the authoring docs, and `extension.Context` all state it) — true in code rather than merely at the accessor's surface: a disabled client must not dial Docker, and must not persist a generated `machine_id` file, to derive a value it would only mask to empty. Conveying the hash rather than the raw id means no new information crosses the process boundary — it is one-way, and the child environment already carries `authToken`.

**Rationale — the timeout**: the derivation's first candidate is a Docker `Info` call on a client built with `FromEnv` and no dial timeout, and the context reaching it on the dispatch path is lstk's root signal context, which carries no deadline. That call now runs *before* the extension execs. Without a bound, a `DOCKER_HOST` that drops packets rather than refusing them — a dead VPN route, a stale remote Docker context, a firewalled host — hangs the dial until the operating system abandons the TCP connect: roughly 75 seconds on macOS and over two minutes on Linux, during which `lstk <ext>` prints nothing and runs nothing, blocked on deriving a telemetry correlation id. A nice-to-have field can never be allowed to cost that. The timeout caps the worst case at 3 seconds, after which the derivation falls through to the `sys_`/`gen_` fallbacks exactly as it does for any other Docker failure. The same unbounded dial previously sat at the end of every telemetry-enabled command — `EmitCommand` built the environment with no deadline — so bounding it inside the accessor fixes the command-exit hang as well, not just dispatch. The price is that a daemon which is alive but slower than 3 seconds to answer `Info` (Docker Desktop mid-startup, say) yields a `sys_`/`gen_` id for that run instead of `dkr_`: bounded latency is bought with cross-run prefix stability in that rare case. A healthy daemon answers in milliseconds, so the timeout is dormant in every ordinary run.

**Alternatives considered**: keeping `MachineID()` a plain no-arg getter and priming the `sync.Once` at the dispatch call site via a discarded `GetEnvironment` call — the design as first implemented (rejected in review on three counts: `GetEnvironment` computed the id unconditionally, so a disabled client still dialed Docker and could persist a `machine_id` file solely to derive a value the getter masks, making the documented "computes neither" contract false; the priming call discards its result, so it reads as a deletable no-op, and deleting it would silently empty the conveyed field with every unit test still green; and it placed the unbounded dial in front of the exec. The symmetry-with-`SessionID()` argument did not survive contact: `SessionID()` reads a field the constructor set, `MachineID` was never a plain field read, and pretending it was is what created the ordering trap). No timeout on the derivation (rejected: the multi-minute pre-exec stall above — "the same lookup happens moments later anyway" was tolerable when it ran after the extension, not in front of it). Bounding only the dispatch call site (rejected: it leaves the identical stall at every command's exit and separates the derivation from its latency policy). Deriving a separate id for extensions (rejected: two derivations that must agree is exactly the failure this change removes).

### Decision 3: `endpointUrl` and `emulators` are independent, and dispatch never rejects an endpoint

`resolveEmulators` is unchanged — `emulators` remains the result of local Docker discovery — and `dispatchExtension` does not call `rejectEndpointURL`.

**Rationale**: the two fields answer different questions ("what is running here" vs. "what was I told to target") and have different consumers; collapsing them would destroy information, since a user can legitimately have a local emulator running while aiming elsewhere. `rejectEndpointURL` exists for built-ins like `start` and `volume` that operate on local Docker state and have no remote equivalent — that is a statement about those commands, not a general policy. lstk cannot know whether a given extension has a remote equivalent, so refusing on its behalf would be a guess; conveying the fact and letting the extension decide is the only position lstk can hold correctly.

**Alternatives considered**: synthesizing an `emulators` entry from the endpoint URL (rejected: lstk does not know the type without probing, and it would misreport a targeted endpoint as a discovered running emulator). Rejecting dispatch when an endpoint source is set unless the extension opts in (rejected: there is no manifest to declare such an opt-in, and adding one to gate a field would invert the contract's manifest-free design).
